# 내 에이전트 실행·수집 구조

2026-09-07 수정. 웹의 매크로 실행은 로컬 실행기를 연결하는 기존 방식을 유지한다. 거래소 키는 실행기 메모리에만 있고 웹 서버는 주문하지 않는다.

## 확인한 원인과 수정

| 문제 | 변경 |
| --- | --- |
| 웹 서버는 수집기를 시작하지 않고 Prefect만 기다림 | FastAPI lifespan에서 수집기를 자동 시작하고 실행 세션 생성 직후 깨움. 새 세션의 첫 RSS는 즉시 공개하고 Prefect가 브라우저·AI 보강을 담당 |
| 첫 RSS 전에 CoinDesk 브라우저 탐색·티커 아카이브를 기다림 | 티커 RSS와 공식 RSS를 먼저 병렬 수집. RSS 결과를 먼저 저장한 뒤 Playwright로 공개 섹션·태그·검색 페이지를 추가 수집 |
| Prefect 롤링 배포 때 이전 프로세스가 새 스케줄을 정지 | `pause_on_shutdown=False`, 커밋 버전 표시, 60초 스케줄과 300초 티커 수집 간격 분리 |
| 알려진 티커도 한국어 검색만 수행 | 한국어 이름과 영문 프로젝트 이름을 함께 검색. 미등록 단축 티커는 토큰 문맥을 요구하고 ENA/Ethena·TAO/Bittensor 등 별칭 및 시세 페이지 제외 적용. 최근 결과가 있으면 5년 아카이브 검색 생략 |
| RSS를 받은 뒤에만 중복 분석 잠금 | RSS 요청 전에 DB 티커 lease 획득. 웹·Prefect·다른 사용자 간 중복 수집 방지 |
| 순서 무관 fingerprint에 새 기사 순서만 덮어씀 | 저장된 기사와 분석 순서·번역을 함께 유지하고 소스 메타데이터만 갱신 |
| 조회마다 제목 번역, 일부 번역 실패가 건별 유료 재시도로 확대 | 수집 단계에서 번역을 저장. 에이전트 GET은 DB만 읽음. 번역은 배치 1회, 원문 대체, 공용 일일 예산 적용 |
| AI 예산 소진 후에도 브라우저 본문 추출 | 예산이 없으면 RSS 제목·기존 발췌로 반환. 외부 본문 요청 생략 |
| 첫 뉴스 확인이 5분 뒤, WebSocket 장애 시 상태 정지 | 첫 수집은 3초, 준비된 뉴스는 30초마다 DB 확인. WebSocket 장애·응답 지연 시 5초 HTTP 복구 조회 |
| 차트 로딩 실패가 포지션 손실 알림도 막음 | 평가손익 알림은 실행기 상태만으로 표시 |
| 고래 모듈이 준비 중 상태로 아무 이벤트도 생성하지 않음 | 인증된 세션의 현물/선물 대규모 체결 조회와 표시 추가 |
| 종료한 세션이 선택 목록에서 사라짐 | 최근 정상 종료·오류 세션을 남겨 사용자가 결과를 확인 가능 |
| 단순 종료·청산 실패도 무포지션으로 저장 | 최종 스냅샷 기준 저장. 구버전은 마지막 보유 상태 유지, 명시적인 청산 성공 보고만 반영 |
| 주문 접수를 체결로 간주, 타임아웃 후 주문 재전송 | 실행기 v6는 체결 완료 확인. 응답 불명확 시 같은 client ID로 조회하고 중복 시장가 주문은 보내지 않음 |
| 시세 오류 동안 원격 종료 명령을 못 받음 | 시세 조회 실패 중에도 실행기 heartbeat 유지 |

## 동작 흐름

1. 사용자가 웹에서 실행기를 연결하고 실행기에서 매크로를 시작한다.
2. `/api/runner/start`가 계정 소유 실행 세션을 저장하고 수집기를 깨운다.
3. 수집기는 최근 heartbeat가 있는 실행 티커 중 수집 시각이 된 종목만 조회한다. 같은 자산의 USDT/USDC 마켓은 뉴스 하나를 공유한다.
4. DB lease를 획득한 프로세스만 RSS를 요청한다. 기사 도착 즉시 규칙 분석 스냅샷을 먼저 공개한다. Prefect는 별도 태스크에서 CoinDesk·Decrypt·CryptoSlate 공개 페이지를 Playwright로 수집하고 합친 결과에 AI 요약·번역을 최대 한 번 적용한다.
5. 내 에이전트는 실행 상태, 뉴스, 포지션 손익·변동성, 대규모 체결을 각자 갱신한다. 한 소스 장애가 나머지 표시를 막지 않는다.
6. 청산 후 종료 버튼은 `stop_mode=close_and_stop`을 요청한다. 실행기 확인 전에는 완료로 표시하지 않는다. 최종 보고를 받은 뒤 종료 결과를 남긴다.
7. 종료·heartbeat 만료 티커는 다음 수집 대상에서 제외한다. 마지막 스냅샷은 보존 기간 동안 조회할 수 있다.

## 알림 생성 기준

채팅에는 새로운 기사·대규모 체결·전략 신호와 실행 상태의 실제 변화만 추가한다. 연결 정상, 체결 없음, 새 신호 없음, 뉴스 수집 대기·결과 없음은 메시지로 생성하지 않는다. 현재 실행·포지션 상태는 상단 상태 표시에서 확인한다.

화면 세션은 최근 이벤트 200개와 중복 판정용 ID 2,000개를 메모리에 보존한다. 조회 시각은 기존 메시지의 발생 시각을 덮지 않으며, 기사 번역이 보강돼도 새 알림으로 세지 않는다. 같은 봉의 전략 신호는 배열 위치가 이동해도 동일한 ID를 쓴다. 지속적인 소스 장애는 한 번만 알리고, 재시도 중에는 회복으로 판정하지 않는다.

평가손실은 2% 이상 구간 진입과 추가 2%p 악화 시 알리고, 1.5% 미만으로 회복한 뒤 재진입하면 다시 알린다. 변동성도 위험 구간 진입·심화 시에만 알리며, 임계값 근처의 작은 진동이나 평시 점검은 알림으로 만들지 않는다. 이 처리는 프론트에서 수행하므로 추가 API 호출이나 DB 쓰기는 없다.

## 비용·DB·캐시

- `POSITION_NEWS_EMBEDDED_ENABLED=true`: 웹 내 수집기. 외부 워커 전용 운영에서는 false로 끌 수 있다.
- `POSITION_NEWS_EMBEDDED_BOOTSTRAP_ONLY=true`: Render 웹은 신규·오래된 티커의 RSS만 복구하고 워커에 lease를 넘긴다. 웹에서 Chromium 설치나 유료 호출을 기다리지 않는다. 독립 로컬 운영에서는 false로 전체 수집을 수행한다.
- `POSITION_NEWS_SCHEDULE_SECONDS=60`: Prefect 스케줄 확인 간격. 실제 같은 티커 재수집은 300초 DB 커서로 제한한다.
- `POSITION_NEWS_BROWSER_ENRICHMENT_ENABLED=true`, `POSITION_NEWS_BROWSER_BUDGET_SECONDS=35`: 워커에서 RSS 유무와 무관하게 브라우저 보강. Render 기본 1개 탭(로컬 기본 3개), 섹션·태그 JavaScript 비활성·검색만 활성, 이미지·영상·폰트 제외, 공유 페이지 15분·실패/빈 결과 5분 캐시. 공개 페이지 캐시는 Postgres에도 최대 512개 저장해 Prefect의 새 프로세스에서도 재사용한다.
- HTTP 429는 출처 호스트별 대기 상태로 DB에 공유한다. `Retry-After`(기본 5분, 최대 24시간)가 지나기 전에는 신규 티커에서도 해당 출처에 재요청하지 않으며, 다른 출처와 기존 뉴스 표시는 유지한다.
- `POSITION_NEWS_SCAN_SECONDS=5`: 실행 티커 확인 주기. 시작 요청은 이 주기를 기다리지 않고 깨운다.
- `POSITION_NEWS_COLLECTION_SECONDS=300`: 티커별 RSS 재수집 간격. 첫 티커에는 대기하지 않는다. 오류/빈 결과는 60초부터 제한적으로 재시도한다.
- `POSITION_NEWS_MAX_AI_ANALYSES_PER_RUN=2`, `POSITION_NEWS_MAX_AI_ANALYSES_PER_DAY=10`: 공용 분석 상한. 기본 모델은 Haiku. 기사 fingerprint가 같으면 분석 재사용.
- `POSITION_NEWS_TRANSLATION_MAX_CALLS_PER_DAY=10`: 에이전트 수집 번역 상한. `NEWS_TRANSLATION_MAX_CALLS_PER_DAY=20`은 공개 뉴스와 에이전트가 공유하는 전체 제목 번역 상한이다. 번역 실패·예산 소진 시 원문을 제공한다.
- 공개 코인 뉴스는 완료 스냅샷 우선. fallback RSS도 동시 요청을 합치며 빈 결과를 60초 캐시한다. 캐시 hit에서 번역을 다시 실행하지 않는다.
- 뉴스·번역 저장소와 일일 예산은 DB에 있으므로 재시작이나 프로세스 추가로 초기화되지 않는다. 웹과 Prefect는 반드시 같은 Postgres를 사용한다.
- `RunSession(status,last_heartbeat_at)` 복합 인덱스로 현재 실행만 조회하며 매크로 JSON 전체를 읽지 않는다. API 인증과 소유권·스냅샷 조회는 요청별 DB 세션을 공유한다.
- 웹 수집기는 보존 기간 정리를 매 스캔 대신 시간당 1회 실행한다.
- 대규모 체결은 티커·시장별 30초 공유 메모리 캐시, 동시 요청 합치기, 오류 재시도 제한을 사용한다. 최대 512키이며 AI와 주기적인 DB 쓰기는 없다. 프로세스 간에는 별도 캐시이므로 인스턴스 수에 비례해 조회가 증가할 수 있다.

## 고래 체결의 의미

새 기능은 특정 고래 투자자의 지갑이나 보유 종목을 식별하지 않는다. 바이낸스 공개 `aggTrades`의 최근 최대 500건 중 10분 이내이며 기본 100,000 USDT/USDC 이상인 체결 표본이다. 전체 거래를 빠짐없이 수집하는 스트림은 아니다. 화면에도 범위와 의미를 표시한다. API의 `m`은 매수자가 maker인지 나타내므로 `m=false`를 적극 매수, `m=true`를 적극 매도로 표시한다. [바이낸스 공개 체결 API](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints)

## 운영 반영

- 백엔드와 프론트엔드 배포가 필요하다. 백엔드 시작 시 새 collection lease 컬럼과 인덱스를 SQLite/Postgres에 추가한다. 테이블 삭제나 데이터 초기화는 하지 않는다.
- 운영 Render에서는 별도 Prefect 워커가 브라우저·AI 보강을 담당한다. 웹과 워커를 함께 배포하며, Prefect 배포가 unpaused인지, 새 버전에서 RSS·브라우저·저장 태스크가 완료되는지 확인한다. 웹의 첫 RSS와 오래된 뉴스 복구는 워커 장애 중에도 작동한다.
- 실행기 `runner-v6` Windows 릴리스 게시·체크섬 확인 후 다운로드 URL과 버전·최소 버전을 6으로 전환한다. 이미 실행 중인 v5의 heartbeat·종료 보고는 호환 처리하며, 새 웹 빠른 연결은 v6 업데이트를 안내한다. 불명확한 체결은 `position_uncertain`으로 보존하고 화면에 포지션 확인 필요를 표시한다.
- Vercel 프론트엔드는 HTTP를 Render로 프록시하고 WebSocket은 Render로 직접 연결한다. 별도 도메인에서는 `VITE_API_WS_BASE`를 설정한다. WebSocket이 실패해도 HTTP 갱신은 계속된다.
- 실행기는 사용자의 PC에서 실행된다. PC를 끄거나 실행기를 종료하면 웹에서 거래소 주문을 대신 실행할 수 없다. 연결이 없으면 요청 상태와 마지막 확인 상태를 표시한다.

## 검증

- 격리 SQLite를 사용하는 백엔드 회귀 테스트 및 실제 FastAPI lifespan을 이용한 시작 → 신규 티커 수집 → 뉴스 조회 → 청산 요청 → 최종 상태 저장 통합 테스트.
- 프론트엔드 단위 테스트, Vite production build, 실제 Chromium에서 모의 API를 이용한 뉴스 도착·포지션 위험·대규모 체결·WebSocket 장애 복구·종료 화면 유지 검증.
- 실행기 테스트는 거래소 모의 응답으로 접수/체결 구분, 타임아웃 후 중복 주문 방지, 시세 장애 중 종료 명령 수신을 확인한다. 실거래 주문이나 운영 계정 변경은 실행하지 않았다.
- 공개 RSS를 실제 조회한 단일 측정에서 LINK 10건(1.16초), SC 1건(0.85초), BMT 7건(0.72초)을 확인했다. 결과 수와 지연은 소스 상태에 따라 달라진다.
- Windows GitHub Actions에서 실행기 전체 테스트와 exe 빌드가 통과했다. `runner-v6` 공개 자산 20,123,920바이트를 다운로드해 SHA-256 `432abbf693d0d778ba0ed3b702cc383cdf0b91533d4a39cb6ad5049d6357f324` 일치를 확인했다.
- 배포 전 최종 회귀: 백엔드 685개, 프론트엔드 34개 통과. 로컬 실행기는 50개 통과·Windows 전용 1개 제외이며 Windows 빌드에서는 해당 플랫폼 테스트까지 실행했다. 실제 거래소 주문 검증은 수행하지 않았다.

운영 Playwright 전체 실패는 Prefect enrichment 태스크와 flow를 Failed로 표시합니다. RSS를 보존하고 최종 분석을 한 번만 수행한 뒤 실패를 기록하며 자동 유료 재시도는 하지 않습니다. 일부 소스 장애는 성공 수·단계·짧은 오류 메시지를 기록합니다.
