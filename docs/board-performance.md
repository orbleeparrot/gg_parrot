# 게시판 로딩 개선 — 2026-09-10

## 원인과 측정 결과

개발 FastAPI/Vite 서버에서 동일한 원격 PostgreSQL을 사용해 변경 전후를 비교했다. 게시글은 32개이며, 상세 조회 표본은 사진 4장·댓글 3개가 있는 글이다. 운영 배포 후 성능이나 부하 테스트 결과를 의미하지 않는다.

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 목록 API, 비로그인·10개 | 797–837ms | 387–414ms |
| 상세 API, 조회수 최초 반영 | 3,619ms | 1,326ms |
| 상세 API, 조회수 중복 제외 | 2,623–2,654ms | 945–960ms; 별도 1,921ms 표본 1회 |
| Vite 첫 목록 화면 표시 | 1,688ms | 1,457ms |
| Vite 사진·댓글 있는 상세 화면 표시 | 4,815ms | 2,877ms |
| Vite 사진·댓글 없는 상세 화면 표시 | 2,863ms | 1,901ms |
| 첫 목록의 JS 리소스 | 70개 / 디코딩 후 3,182,181바이트 | 46개 / 디코딩 후 2,052,092바이트 |

브라우저 수치는 각 시나리오의 단일 실행 표본으로, 중앙값이나 운영 번들 전송량이 아니다. API와 브라우저 측정은 별도 실행이며 서로 더하거나 직접 대응시키지 않는다.

목록 SQL의 실제 DB 실행은 0.442ms였지만, 원격 DB의 단순 `SELECT 1` 왕복은 약 186ms였다. 목록에서는 트랜잭션 시작·정리와 연결 확인 비용, 상세·댓글에서는 여러 번의 DB 질의와 커밋 이후 재조회 비용이 누적됐다. 상세 응답을 만들 때 첨부 이미지 원본까지 읽고, 댓글 작성자마다 아바타를 따로 조회하는 문제도 있었다.

변경 후 상세 조회의 1,921ms 표본은 SQL 시간이 다른 표본과 같은 약 744ms였지만, 전체 DB 처리 시간이 약 1,910ms까지 늘었다. 연결·트랜잭션 처리 구간의 변동이 남아 있으며 이 표본의 추가 지연 원인은 확정하지 않았다.

## 반영 내용

- 공개 목록의 사용하지 않는 계정 조회를 제거했다. 목록 전용 세션만 AUTOCOMMIT으로 읽어 불필요한 트랜잭션 왕복을 줄인다. 풀 반환 시 격리 수준을 복원하며 쓰기 요청은 기존 트랜잭션을 사용한다.
- 상세 응답은 게시글·작성자 아바타·내 추천 여부, 댓글과 아바타, 첨부 메타데이터의 3개 질의로 만든다. 이미지 파일은 별도 이미지 요청에서만 읽는다. 댓글 작성자가 늘어도 상세 질의 수는 늘지 않는다.
- 조회수는 원자적 증가와 `RETURNING`으로 한 번에 처리한다. 같은 방문자의 중복 집계 방지에는 잠금을 적용하고, 커밋 실패 시 예약을 해제해 다음 조회에서 재시도할 수 있게 했다.
- 인증과 게시판 처리가 요청 하나의 DB 세션을 공유한다. 일반 댓글과 답글 등록은 인증을 포함해 모두 3개 질의, 연결 체크아웃 1회로 끝난다. 이전에는 각각 5개·6개 질의가 필요했다.
- 글·댓글 작성/수정, 추천, 신고에서 중간 커밋과 커밋 이후 재조회를 제거했다. 추천은 게시글 행을 잠근 뒤 집계를 갱신한다. 삭제는 이미지 원본을 읽지 않고 일괄 처리한다.
- 비동기 파일 업로드 경로의 동기 DB 처리는 스레드 풀로 옮겼다. 글과 첨부 이미지는 마지막에 함께 커밋해 중간 실패 시 일부만 저장되지 않는다.
- 목록과 상세에서 글쓰기 컴포넌트를 직접 가져오던 의존성을 끊었다. 글쓰기 주소 함수는 별도 모듈로 옮겨 TipTap 편집기를 작성·수정 화면에서만 불러온다.
- 목록은 계정·페이지·검색·정렬별로 메모리에 최대 20개, 30초 동안 보관한다. 새로고침하면 사라진다. 글·댓글·추천 변경 성공 시 즉시 무효화하고 표시 중인 목록을 다시 조회한다. 실패 응답은 저장하지 않는다.
- 변경 전에 시작한 목록 요청은 캐시를 다시 채울 수 없게 했다. 화면 이동 시 요청을 취소하고 오래된 상세 응답이 새 화면을 덮어쓰지 않게 했다.

## 검증

쓰기 검증은 `backend/tests/conftest.py`가 제공하는 격리된 임시 SQLite와 브라우저 API 픽스처에서 수행했다. 실제 계정으로 글이나 댓글을 등록하지 않았다. 개발 서버 GET 상세 검사는 정상 동작에 따라 조회수를 반영할 수 있다.

- 백엔드 36개 테스트 통과: 게시판 기능, 질의 수·이미지 로딩 제한, 댓글·답글, 조회수 커밋 실패 후 재시도, 글쓰기 실패 시 롤백, 요청 단위 세션, 프로필 설정.
- 프런트엔드 캐시·게시판 텍스트·채팅 API·프로필 이미지 API 테스트 통과.
- Vite 프로덕션 빌드 통과.
- 실제 Chromium에서 빌드 결과를 390px/1440px로 검사: 목록 복귀 시 추가 목록 요청 없음, 댓글 실패 시 입력 유지와 재시도, 댓글·추천 후 목록 갱신, 가로 넘침 없음, 작성 화면 진입 시에만 편집기 로딩.

재실행 명령(프로젝트 의존성과 Playwright Chromium 설치 필요):

```sh
cd backend
python -m pytest tests/test_board.py tests/test_board_performance.py tests/test_request_scoped_db.py tests/test_profile_settings.py
```

```sh
cd frontend
node --test tests/boardListCache.test.js tests/boardText.test.js tests/chatApi.test.js tests/profileAvatarApi.test.js
npm run build -- --outDir /tmp/ggp-board-fast-build
FRONTEND_BUILD=/tmp/ggp-board-fast-build BROWSER_EXECUTABLE_PATH=/path/to/chromium python tests/boardPerformanceBrowser.smoke.py
```

원격 DB 왕복 지연 자체와 운영 서버의 콜드 스타트 여부는 이번 코드 변경으로 해결되지 않는다. 운영 배포, DB 지역 변경, 인프라 설정 변경은 수행하지 않았다.
