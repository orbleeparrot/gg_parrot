## 우선 해결할 문제

### 1. 리더보드 GET에서 일일 생성과 집계가 실행된다 — P1

[main.py:948](../../backend/app/main.py#L948)의 비동기 GET은 `ensure_today_carryover()`와 `challenge.ensure_today()`를 순서대로 기다린 뒤 목록을 반환한다. 날짜가 바뀌고 오늘 챌린지가 없으면 [challenge.py:205](../../backend/app/challenge.py#L205)에서 종목 선정, AI 매크로 생성, 최대 3개의 모의매매 세션 시작, 리더보드 저장이 발생한다. 생성 잠금과 DB claim은 중복 생성을 줄이지만 방문자의 대기를 없애지는 않는다.

평상시 [leaderboard.py:379](../../backend/app/leaderboard.py#L379)는 오늘의 모든 항목을 읽고 투표를 집계하며, 응답 객체를 만든 뒤 Python에서 순위를 정렬한다. 왕관 등급도 [leaderboard.py:333](../../backend/app/leaderboard.py#L333)의 프로세스 캐시가 만료되거나 소유자 조합이 바뀌면 해당 소유자의 과거 전체 판매·투표를 다시 읽어 계산한다. 캐시 기본 수명은 180초다.

실제 SQLModel+SQLite 재현에서 오늘 항목 250개, 전체 항목 400개, 투표 4,000개를 넣었을 때 목록 함수는 왕관 캐시 miss에서 쿼리 7회, hit에서도 4회를 실행하고 매번 오늘 항목 250개 전부 반환했다. 이 수치는 인증·챌린지 확인 쿼리를 제외한다. 쿼리 수뿐 아니라 매번 가져오는 행의 양과 집계 비용이 문제다. [SQL 검증](verify_leaderboard_db.py)

[Leaderboard.jsx:119](../../frontend/src/pages/Leaderboard.jsx#L119)는 약 5초 간격으로 목록을 재요청하고, 진입 시 별도로 `/api/challenge/today`도 호출한다. 따라서 일일 생성이 끝난 뒤에도 방문자별로 집계 비용이 반복된다. 폴링 간격에는 응답 시간과 백오프 등이 추가된다.

또한 비동기 라우트 내부에서 동기 DB 조회와 목록 계산을 직접 호출한다. 느린 DB 왕복은 같은 이벤트 루프의 다른 요청에도 영향을 줄 수 있다. 로그인 사용자 인증에 사용한 요청 세션도 일일 생성 대기 전에 열리므로, 동시에 여러 사용자가 기다리면 DB 연결 점유가 커질 가능성이 있다. 운영 풀 고갈은 측정하지 않았다.

실제 함수 본문에 모의 DB 호출 4회×30ms를 넣은 격리 재현에서는 이벤트 루프 heartbeat가 약 125ms 멈췄다. 이 값은 운영 성능 수치가 아니라 동기 호출의 영향을 확인하는 실험이다. [제어 흐름 검증](verify_leaderboard_flow.py)

**개선:** 일일 이월·AI 생성은 재시도 가능한 워커 작업으로 분리한다. 수익률·투표·판매 변경을 반영한 공용 순위 스냅샷을 주기적으로 저장하고 GET은 해당 결과에 개인별 구매·투표 상태만 소량 결합한다. 순위 갱신 주기와 마지막 계산 시각을 정의하고, 생성 실패 시에도 마지막 정상 결과를 읽을 수 있게 한다. 사용자별 잠금·권한 정보는 공용 캐시에 섞으면 안 된다.

### 2. 내 에이전트 뉴스는 먼저 수집된 기사도 대기한다 — P1

대기 구간은 여러 곳이다.

1. [news.py:4145](../../backend/app/news.py#L4145)의 수집은 [http_runtime.py:109](../../backend/app/http_runtime.py#L109)의 `run_parallel()` 전체 결과를 기다린다. 빠른 RSS가 끝나도 느린 다른 수집처가 끝나기 전에는 결과를 반환하지 않는다.
2. [collector.py:335](../../backend/app/agent_features/position_news/collector.py#L335)의 초기 공개는 기존 스냅샷이 신선하면 새 일반 기사가 있어도 `reused`로 끝난다. 커뮤니티 글만 별도 빠른 갱신 예외가 있다. 새 일반 기사는 최종 보강 단계까지 밀린다.
3. [collector.py:223](../../backend/app/agent_features/position_news/collector.py#L223)은 번역·커뮤니티 요약 처리를 거친 뒤 스냅샷 claim·저장을 한다. AI 분석 전 기본 결과 공개도 이 단계 이후다. 초기 RSS 공개 경로는 있으므로 항상 모든 분석을 끝내야만 저장되는 것은 아니지만, 기사별 준비 즉시 공개를 보장하지 못한다.
4. [service.py:244](../../backend/app/agent_features/position_news/service.py#L244)의 GET은 저장 결과를 읽고 다시 `_localize_news_payload()`를 호출한다. 한국어 기사와 번역 대기 기사가 함께 있으면 한국어 기사까지 요청 종료를 기다린다.
5. [usePositionNewsFeature.js:63](../../frontend/src/features/agents/positionNews/usePositionNewsFeature.js#L63)는 응답 단위로 갱신한다. 초기 pending은 3초, 보통 응답은 30초, 번역 대기는 최소 30초 이후 재조회한다. 기사 완료 이벤트를 바로 받는 경로는 없다.

재현 결과: 빠른 RSS 완료 후에도 느린 수집처가 막혀 있으면 결과 미반환; 신선한 기존 기사+새 기사 조건에서 초기 공개 호출 0회; 번역 처리가 막힌 동안 새 스냅샷 0개; GET에 준비된 한국어 기사 1개가 있어도 번역 대기 해제 전에는 응답 미반환. [검증 스크립트](verify_position_news.py)에 이벤트 기반 재현을 남겼다.

**개선:** 기사 ID별로 수집 결과를 즉시 upsert하고 번역·본문·요약·분석 상태를 별도로 갱신한다. 한국어 표시가 준비된 기사부터 조회 가능하게 하고, 다른 기사나 요약 작업은 이를 막지 않게 한다. 현재 스냅샷은 요약용으로 유지할 수 있지만 기사 전달은 단조 증가 revision/cursor 기반으로 분리한다. SSE 또는 변경분 폴링으로 새 기사·수정만 전달하고 재접속 시 cursor 이후를 복구한다. 화면 타임라인은 이미 수신한 기사를 메모리에 보존하지만, 서버의 최신 스냅샷 조회는 기사 이력 재생 API가 아니다.

### 3. 코인 동향 뉴스도 GET에서 수집·번역·요약을 기다린다 — P1

[news.py:3205](../../backend/app/news.py#L3205)의 시장 뉴스는 메모리 캐시가 없으면 수집 → 번역 → 개요 요약 후 응답한다. 개요가 준비되지 않았다는 이유로 이미 준비된 기사까지 대기한다. 일일 개요는 DB에 저장하지만 전체 시장 응답의 캐시는 프로세스 메모리다.

종목 뉴스는 [news.py:4334](../../backend/app/news.py#L4334)에서 완성된 응답 캐시와 중앙 DB 스냅샷을 먼저 읽는다. 하지만 신선한 DB 스냅샷도 다시 동기 번역 처리를 거친다. 이전 결과가 있으면 백그라운드 갱신하는 경로가 있으나, 이전 결과를 반환하기 전에도 번역을 시도한다. 아무 결과도 없는 종목은 요청 중 RSS 수집을 기다린다.

[검증 스크립트](verify_public_news.py)로 시장의 준비된 기사가 개요 요약을 기다리는 것과, 신선한 DB 스냅샷의 한국어 기사가 다른 기사의 번역을 기다리는 것을 재현했다. 모의 대기 구간을 사용했으므로 운영 응답 시간 측정치는 아니다.

**개선:** 시장·경주마 종목도 워커가 미리 수집·번역한 결과를 제공한다. GET은 준비된 기사와 처리 상태만 즉시 반환하며, 데이터가 없으면 수집 작업을 예약하고 빈 pending 결과를 반환한다. 오래된 결과가 있으면 이를 계속 표시한다. 개요 요약은 기사 목록과 독립적으로 갱신한다.

### 4. 번역 대기와 제목별 claim이 DB 왕복을 늘린다 — P1/P2

[news.py:2941](../../backend/app/news.py#L2941)은 다른 프로세스의 번역을 기다릴 때 기본 30초 동안 DB 번역 캐시를 반복 조회한다. 시계를 제어한 재현에서 초기 조회 포함 **18번의 캐시 로더 호출**이 발생했다. 이는 가상의 30초 경과 재현이며 실제 서버에서 30초를 측정한 결과가 아니다. 자체 번역 API 호출 시간은 이 대기 설정과 별개다.

[repository.py:562](../../backend/app/agent_features/position_news/repository.py#L562)의 새 제목 claim은 제목별 `get`과 savepoint insert를 사용한다. 임시 SQLite에서 새 제목 10개를 claim할 때 **SELECT 10 + SAVEPOINT 10 + INSERT 10 + RELEASE 10 = SQL 40개**, 번역 저장은 UPDATE 10개를 확인했다. 트랜잭션 commit 호출은 이 SQL 카운트와 별개다. PostgreSQL의 실제 실행 계획·드라이버 왕복 수는 추가 검증이 필요하다.

**개선:** HTTP 조회에서 기다림·claim·번역을 제거한다. 워커의 claim은 충돌 제어와 lease/fencing을 유지하면서 배치 조회·upsert로 바꾼다. 중복 과금을 막는 기존 장치를 단순 삭제해서는 안 된다. 준비된 번역만 결합하고 미완료 상태를 즉시 반환한다.

### 5. 채팅은 변화가 없어도 전체 조회를 반복한다 — P1

[ChatBox.jsx:259](../../frontend/src/components/ChatBox.jsx#L259)는 채팅창 열림 여부와 무관하게 약 3초마다 최신 메시지를 조회한다. 숨긴 브라우저 탭은 멈추지만, 리더보드가 보이는 상태에서 채팅창만 닫아도 요청은 계속된다. [main.py:1051](../../backend/app/main.py#L1051)은 `before_id`, `seen_id`만 지원하고 새 메시지만 받는 `after_id`는 없다.

[chat.py:126](../../backend/app/chat.py#L126)은 최근 메시지 전체와 최신 ID·읽지 않은 수를 구한다. 인증·읽음 상태·본문 조회가 서로 다른 세션을 사용한다.

| 로컬 fixture: 메시지 250개, 로그인 사용자 | SELECT | 연결 대여 | 반환 메시지 |
|---|---:|---:|---:|
| 일반 최신 조회 | 6 | 3 | 200 |
| 변경 없는 동일 조회 | 6 | 3 | 200 |
| 매크로·답장 포함 | 9 | 3 | 200 |

일반 조회 두 번은 동일한 35,352바이트 JSON을 각각 생성했다. 실제 전송 압축 크기나 운영 메시지 평균 크기는 아니다. [검증 스크립트](verify_chat.py)는 실제 인증·채팅·비속어 검사 모듈과 생성한 임시 DB 데이터를 사용한다.

**개선:** 닫힌 창은 읽지 않은 수·최신 revision만 저비용으로 확인한다. 열린 창은 bounded `after_id` 조회나 이벤트 전달을 사용한다. 단, 삭제·수정·프로필 변경도 전달할 수 있어야 하므로 신규 ID만으로 모든 변경을 판정하면 안 된다. 요청 세션을 공유하고, 읽음 확인은 단조 증가 upsert와 배치 반영을 검토한다. 기존 회원 구분·자정 초기화·권한·읽음 동기화는 보존한다.

### 6. 프론트엔드의 갱신 경로에도 불필요한 작업과 오래된 상태 우선 문제가 있다 — P2

- [News.jsx:435](../../frontend/src/pages/News.jsx#L435)는 이미지 재조회 결과를 `marketRefresh.data || marketState.data`로 우선한다. 이미지 응답이 한 번 설정되면 뒤늦게 도착한 번역 완료 응답이 기본 상태에 있어도 이전 이미지 응답에 가려질 수 있다. 별도 상태 둘 대신 단일 캐시에서 revision에 따라 합쳐야 한다. 이는 코드 경로 확인이며 이번 작업에서 브라우저 화면 재현은 하지 않았다.
- [News.jsx:43](../../frontend/src/pages/News.jsx#L43)는 경주마 최대 10종목을 동시 2개씩 요청한다. 뒤쪽 종목은 앞선 느린 응답에 대기한다. 제한 자체는 과부하 방지에 유효하므로 무조건 동시성을 늘리기보다, 실제 보이는 종목을 먼저 요청하고 DB 배치 조회 API를 제공하는 편이 낫다.
- 리더보드의 초 단위 카운트다운이 열린 채팅까지 다시 렌더한다. [chatStore.js:74](../../frontend/src/lib/chatStore.js#L74)는 변경 없는 응답도 누적 이력을 합치고 정렬한다. 오래 사용하거나 과거 메시지를 많이 읽을수록 CPU/DOM 비용이 커질 수 있다. 카운트다운 분리, 변경 없는 객체 재사용, 긴 이력 가상화를 검토해야 한다. 실제 브라우저 CPU 기여도는 아직 측정하지 않았다.

### 7. 백그라운드 정리 빈도도 줄일 여지가 있다 — P2

[runtime.py:40](../../backend/app/agent_features/position_news/runtime.py#L40)의 내장 워커는 기본 5초 간격으로 수집 대상을 확인한다. [collector.py:581](../../backend/app/agent_features/position_news/collector.py#L581)은 대상이 0개여도 커뮤니티 요약 정리를 실행한다. 스냅샷 정리는 시간 단위로 제한했지만 요약 정리는 같은 제한이 없다. 실제 재수집 간격 300초와 이 확인 간격은 다른 설정이다.

**개선:** 만료 데이터 정리는 별도 시간 단위 작업으로 옮기고, 여러 웹 프로세스가 같은 정리를 반복하지 않도록 실행권을 공유한다. `render.yaml`의 내장/별도 워커 설정은 확인했으나 운영에서 실제 몇 개가 실행되는지는 검증하지 않았다.

### 8. 조회에서 실행하는 일일 이월의 실패 복구도 보완해야 한다 — P2

[leaderboard.py:443](../../backend/app/leaderboard.py#L443)는 실제 이월보다 먼저 당일 마커를 저장한다. 이후 이월이 실패해도 [leaderboard.py:544](../../backend/app/leaderboard.py#L544)의 다음 호출은 마커 존재만 보고 건너뛴다. 실제 함수 본문의 의존성을 제어한 재현에서 첫 작업 실패 후 두 번째 호출은 재시도 없이 완료 날짜를 설정했다. 운영에서 이월이 실제 누락됐다는 의미는 아니다.

**개선:** 예약·실행 중·완료·실패를 구분하고, 이월을 재실행 가능하게 만들어야 한다. 단순히 현재 함수를 크론으로 옮기기만 하면 실패 복구 문제는 남는다. [제어 흐름 검증](verify_leaderboard_flow.py)

## 이미 적용된 최적화

- 에이전트 최신 스냅샷은 상태 PK → 스냅샷 PK의 SELECT 2회다. 기사 수만큼 조회하는 N+1 구조가 아니다.
- 에이전트 GET은 번역 전에 요청 DB 트랜잭션을 rollback하여 연결을 반환한다. 번역을 기다리는 시간 전체에 같은 DB 연결을 붙잡는 구조는 아니다.
- 리더보드 모의매매 상태, 채팅 아바타·답장·잠금 상태는 배치 조회한다.
- 종목 뉴스의 완성 응답 캐시, 오래된 결과 우선 반환, 공유 번역 캐시, 중복 수집/분석 claim이 있다.
- 뉴스 재방문 캐시와 숨긴 탭의 폴링 정지, 폴링 요청 중첩 방지가 있다.
- 채팅의 평상시 GET은 매번 읽음 상태를 쓰지 않는다. 신규 사용자의 상태 초기화와 명시적 읽음 반영은 별도다.
- 관련 PK·일자·사용자 인덱스가 이미 있다. 운영 실행 계획 없이 '인덱스가 없어서 전부 느리다'고 단정할 근거는 없다.

## 수정 순서와 합격 기준

1. 리더보드 GET에서 일일 생성·외부 API·집계를 제거한다. 날짜 전환과 워커 실패에도 GET은 마지막 정상 결과를 반환해야 한다. 평상시 페이지 방문 수가 늘어도 공용 순위 계산 횟수는 늘지 않아야 한다.
2. 모든 뉴스 GET에서 외부 수집·AI 번역 대기를 제거한다. 느린 수집처·기사 B·요약 작업을 멈춰도 준비된 기사 A는 먼저 DB에 저장되고 읽혀야 한다. 기존 기사와 분석 결과는 후속 처리 실패로 사라지면 안 된다.
3. 채팅 전체 폴링을 변경분 전달로 바꾼다. 새 소식이 없으면 200개 재전송·전체 재집계가 없어야 하며, 닫힌 창도 NEW 배지는 정확히 유지해야 한다.
4. 제목 claim 배치 처리, 과도한 정리 주기, 프론트엔드 상태 충돌·렌더링을 정리한다.
5. 운영에 이미 있는 [Server-Timing/요청 로그](../../backend/app/observability.py#L181)의 `app`, `db`, `sql`, `upstream` 시간을 수집해 cold/warm·로그인/비로그인·자정 전후·동시 접속별로 비교한다. DB span은 SQL 및 연결/트랜잭션 시간을 포함하므로 단순 합산하면 안 된다. 느린 쿼리는 실제 행 수와 PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`로 확인한다.
