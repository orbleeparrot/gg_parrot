# 실행기 국내 거래소 — 업비트 · 빗썸 실거래 설계

작성 2026-10-06 · 상태 승인 대기

## 0. 한 줄 요약

GUI 매크로 실행기가 업비트 · 빗썸 원화 현물 주문을 낸다. 거래소 호출을 어댑터 하나
뒤로 모으고, 두 거래소에 없는 테스트넷 자리를 **모의 모드와 리허설**로 채운다.
바이낸스 실거래 경로는 한 글자도 바뀌지 않는다.

## 1. 왜 만드는가

업비트 · 빗썸 매크로는 지금도 **만들 수 있고 백테스트도 된다.** 그런데 실전으로
나갈 길이 하나도 없다.

- `backend/app/runner.py` 의 `_require_binance_macro` 가 세 곳에서 막는다
  (세션 시작 · 런치 티켓 발급 · 티켓 청구).
- `backend/app/realtrade.py` 의 `build_bundle` 도 거부한다.
- GUI 실행기는 `macro["exchange"]` 를 **읽지도 않는다.** `python-binance` 의
  `Client` 하나에 묶여 있다.

"만들 수는 있는데 돌릴 수는 없는 기능" 이 이미 제품에 있다. 프로 빌더 2차(조건 ·
위험관리 확장, 포트폴리오)가 이 위에 얹히므로, 먼저 막지 않으면 구멍만 커진다.

## 2. 이번에 하는 것과 안 하는 것

| | |
| --- | --- |
| **한다** | GUI 실행기 + 서버 신호 경로로 업비트 · 빗썸 원화 현물 실거래 |
| **한다** | 테스트넷이 없는 자리를 메울 모의 모드와 리허설 |
| **안 한다** | 봇 번들(`realtrade.py` 의 zip). 바이낸스 전용으로 남기고 거부 문구만 정확히 한다 |
| **안 한다** | 다종목 · 새 매매 방식 · 위험관리 확장 — 다음 단계 |

봇 번들을 빼는 이유: 번들은 서버 없이 혼자 도는 단순화 실행기라 **전략 판단까지**
거래소별로 다시 써야 한다. GUI 실행기는 지표형 규칙의 진입 · 청산을 서버가
판단하므로(`runner.py` 의 `needs_signals`) 주문 계층만 바꾸면 규칙이 전부 따라온다.
같은 결과를 절반의 면적으로 얻는다.

## 3. 원칙

| 원칙 | 뜻 |
| --- | --- |
| **바이낸스 불변** | 지금 돌아가는 실거래를 건드리지 않는다. 로직을 어댑터로 **옮기되 바꾸지 않고**, `runner/test_macro_runner_execution.py` 의 시험 20 개가 손대지 않은 채 녹색인 것이 증명이다. |
| **비밀키는 이 PC를 떠나지 않는다** | 서버가 주문을 내면 허용 IP 문제가 사라지지만 대가가 거래소 비밀키 업로드다. `credentials.py` 와 `_build_start_payload` 가 지키는 약속이고, 한 번 깨면 되돌릴 수 없다. |
| **거래소 사정은 어댑터 안에** | 수수료 모델 · 주문 파라미터 · 체결 조회가 봇 본문으로 번지지 않는다. 봇은 돈과 수량으로만 말한다. |
| **돈이 나가기 전에 리허설** | 테스트넷이 없는 거래소에서 첫 주문이 인증 · 권한 · 최소 금액으로 실패하면 안 된다. 세션 시작에 확인한다. |

## 4. 어댑터

### 4.1 지금 모양

실행기가 거래소를 부르는 지점은 11 곳이고 **그중 7 곳이 선물 전용**이다. 국내는
스키마가 현물 · 롱 · 1 배로 이미 막고 있으므로(`engine/schema.py`), 국내 어댑터가
덮어야 할 것은 현물 6 가지뿐이다 — 계정 확인 · 현재가 · 주문 규격 · 시장가 주문 ·
주문 조회 · 체결 조회.

### 4.2 인터페이스

```
ensure_ready()                                    # 계정 확인 (바이낸스는 선물 설정 포함)
price() -> float
order_rules() -> OrderRules(step, min_notional)
place_entry(*, notional, price, client_id) -> Order
place_exit(*, base_qty, client_id, reduce_only) -> Order
fetch_order(client_id) -> Order
```

진입이 **수량이 아니라 금액**을 받는 것이 첫 번째 판단이다. 업비트 시장가 매수는
수량이 아니라 원화 총액을 보내므로(`ord_type=price`), 금액을 그대로 넘기면 수량
반올림이 사라져 더 정확하다. 바이낸스는 지금 쓰는 `_order_qty` 를 어댑터 안으로
그대로 옮겨 `notional → qty` 를 똑같이 계산한다.

### 4.3 정규화된 주문

```
Order(status, executed_qty, avg_price, acquired_qty, fees_known)
```

`status` 는 `FILLED | CANCELED | REJECTED | OPEN` 넷으로 좁힌다.

**수수료 계산을 어댑터로 내리는 것이 두 번째 판단이다.** 바이낸스 현물은 매수
수수료를 기초자산에서 떼므로 `fills[].commission` 을 빼야 실제 보유 수량이 나온다
(`macro_runner.py` 의 `acquired`). 업비트 · 빗썸은 수수료를 원화에서 떼므로
**체결 수량이 그대로 보유 수량이다.** 이 차이를 봇 본문에서 분기하면 가장 예민한
코드에 거래소 지식이 번진다.

어댑터가 `acquired_qty` 와 `fees_known` 을 채워 돌려주면, 봇이 쥔
`position_uncertain` · 먼지 수량 · 부분 청산 판단은 그대로 둔 채 두 거래소에서
똑같이 선다.

### 4.4 이름과 자리

어댑터는 `runner/brokers.py` 에 두고 봇은 `self.broker` 로 쥔다. `self.client` 라는
이름은 **쓰지 않는다** — 기존 시험 20 개가 `bot.client` 를 `python-binance` 의 날
클라이언트로 알고 단언하기 때문이다(§10.1). 어댑터 안에서 그 날 클라이언트는
`self.raw` 다.

클래스는 `BinanceBroker` · `DomesticBroker` · `MockBroker` 셋.

**새 의존성을 넣지 않는다.** JWT(HS512)는 HMAC-SHA512 라 `hmac` · `hashlib` ·
`base64` 로 충분하고, HTTP 는 이미 있는 `requests` 를 쓴다. 실행기는 PyInstaller 로
exe 를 만들므로 의존성 하나가 빌드 · 서명 · 배포에 전부 걸린다.

### 4.5 바이낸스 구현 — 이동이지 변경이 아니다

`BinanceBroker` 가 지금 11 개 호출을 그대로 감싼다. 선물 7 개 포함. 호출 인자 ·
재시도 횟수 · 터미널 상태 집합 · 평균가 보정 순서를 바꾸지 않는다.

### 4.6 국내 구현 — 하나가 둘을 덮는다

`DomesticBroker` 하나가 업비트와 빗썸을 덮되, **베이스 URL 만 다른 것이 아니다.**

이 설계의 초고는 `data/krw.py` 가 두 거래소의 **공개 시세**에 같은 `/v1/...` 경로를
쓴다는 데서 사설 API 도 같으리라 추론했다. 그 추론은 틀렸다. 두 거래소의 공식
문서를 직접 확인한 결과는 아래와 같다 — 모양은 닮았지만 경로 · 서명 알고리즘 ·
필드 이름이 제각기 다르다. 그래서 어댑터는 **거래소별 사양 표**를 들고 이름만
갈아 끼운다.

| | 업비트 | 빗썸 |
| --- | --- | --- |
| 베이스 | `https://api.upbit.com` | `https://api.bithumb.com` |
| 주문 생성 | `POST /v1/orders` | `POST /v2/orders` |
| 주문 유형 필드 | `ord_type` | `order_type` |
| 클라이언트 주문 ID | `identifier` (최대 64 자) | `client_order_id` (1–36 자, 영숫자 · `-` · `_`) |
| 응답의 주문 ID | `uuid` | `order_id` |
| JWT 서명 | HS512 | **HS256** |
| JWT 페이로드 | `access_key` · `nonce` | `access_key` · `nonce` · **`timestamp`**(ms) |

같은 것: `market` · `side`(`bid`/`ask`) · 시장가 매수는 `price`(원화 총액) · 시장가
매도는 `volume` · `query_hash`(쿼리 스트링의 SHA512) + `query_hash_alg: "SHA512"` ·
`Authorization: Bearer <JWT>`. 토큰은 요청마다 새로 만든다(재사용하면 인증 실패).

클라이언트 주문 ID 가 36 자로 좁은 쪽(빗썸)에 맞춘다. 지금 쓰는
`"ggp-" + uuid4().hex[:28]` 은 32 자라 양쪽에 들어간다.

리허설(`POST /v1/orders/test`)은 업비트에만 있다 — §5.3.

체결 값은 `trades[]` 에서 만든다 — `avg_price = Σ funds / Σ volume`,
`acquired_qty = executed_volume`(수수료가 원화에서 빠지므로 차감 없음),
`fees_known = (Σ trades.volume == executed_volume)`. 바이낸스 쪽 계산과 모양이 같아
봇에서 보면 구분되지 않는다.

**상태는 체결량을 먼저 보고 접는다.** 시장가 주문은 쓰고 남은 잔액이 취소되면서
`state=cancel` 로 끝날 수 있다 — 빗썸 문서가 `ioc` 에 대해 "일부 체결(잔량 즉시
취소) → done", "체결 없음 → cancel" 로 적고, 업비트 문서는 시장가 매수의 최종
상태를 명시하지 않는다. 명시되지 않은 것을 사실로 적을 수는 없으므로, 양쪽 어느
쪽이든 안전한 규칙을 쓴다:

| 거래소가 준 것 | 접은 `status` |
| --- | --- |
| `done` | `FILLED` |
| `cancel` 인데 체결량 > 0 | `FILLED` — 더 일어날 일이 없고 그만큼 샀다 |
| `cancel` 인데 체결량 0 | `CANCELED` |
| `wait` · `watch` | `OPEN` |
| 응답 없음 | `UNKNOWN` |

체결량을 먼저 보지 않으면 **정상 체결된 매수마다 봇이 "체결 완료를 확인하지
못했습니다" 로 멈춘다.** 거래소가 쓴 낱말은 `raw_status` 로 그대로 보존해 사람에게
보고한다.

선물 메서드는 호출되면 예외를 던진다. 스키마가 국내 선물 매크로를 거부하므로
도달할 수 없는 경로이고, 조용히 성공하는 것보다 터지는 편이 낫다.

### 4.7 멱등성

지금 실행기는 `newClientOrderId` 로 주문을 보내고 응답이 없으면 **재주문하지 않고
같은 ID 로 다시 조회한다.** 타임아웃은 거절의 증거가 아니기 때문이다.

업비트의 `identifier`(계정 내 고유 · 최대 64 자)가 정확히 같은 물건이고
`GET /v1/order?identifier=` 로 되찾을 수 있다. 그래서 이 규칙은 두 거래소에서 글자
그대로 같다. 어댑터는 `client_id` 를 받아 각자의 자리에 넣을 뿐이다.

## 5. 모의 모드

### 5.1 왜

실행기는 테스트넷을 기본값으로 두고 메인넷은 따로 확인을 받는다
(`macro_runner.py` 의 `testnet = not self.live.get()`). 서버도 웹에서 띄우는 티켓을
테스트넷으로 강제한다. 그런데 **업비트 · 빗썸에는 테스트넷이 없다.** 그대로 두면
국내 매크로는 첫 실행부터 전부 실제 돈이고, 바이낸스 사용자가 누리는 "먼저 돌려
본다" 가 사라진다.

모의 모드가 그 자리를 대신한다. 세 거래소가 **같은 모양**이 되는 것이 부수 효과가
아니라 목적이다 — 거래소마다 안전망이 다르면 사용자가 어디서 안전한지 모른다.

### 5.2 어떻게

모의는 어댑터를 **감싸는 데코레이터**다. 읽기는 진짜 거래소로 보내고 주문만
삼킨다.

| | 모의에서 | 키가 필요한가 |
| --- | --- | --- |
| 현재가 | 진짜로 읽는다 | 아니오 (공개 시세) |
| 주문 규격 · 수수료율 | 키가 있으면 진짜로 읽고, 없으면 거래소별 기본값을 쓰며 그 사실을 기록한다 | 선택 |
| 잔고 | **읽지 않는다.** 매크로의 `initial_capital` 에서 출발하는 가상 잔고를 쓴다 | 아니오 |
| 주문 | **보내지 않는다.** 그 순간 현재가로 전량 체결한 것으로 치고 `Order` 를 만든다 | 아니오 |
| 수수료 | 위에서 얻은 수수료율로 계산해 반영한다 | — |

모의가 **키 없이도 돌아야** 연습이 된다. 그래서 키가 필요한 읽기는 모두 선택이고,
없으면 기본값으로 내려간다. 반대로 키가 있으면 진짜 값을 읽어 실전과 같은 숫자로
연습한다 — 이 두 가지가 모의 모드의 유일한 차이다.

바이낸스에도 같은 데코레이터가 걸린다. 바이낸스는 테스트넷이 **따로** 남는다 —
테스트넷은 거래소가 주는 가짜 체결이고 모의는 우리가 만드는 가짜 체결이라, 둘은
겹치지 않고 각자 쓸모가 있다.

### 5.3 리허설

모의 모드가 장난감이 되지 않으려면, 모의로 잘 돌다가 실전 첫 주문에서 멈추는 일을
막아야 한다. 세션을 시작할 때 **한 번** 확인한다.

- 국내: `POST /v1/orders/test` 를 이번 매크로의 실제 주문 모양으로 친다. 문서가
  "실제 주문을 생성하지 않고 주문 요청 형식과 주문 가능 여부를 검증한다" 고
  명시한다. 키 · 허용 IP · 주문 권한 · 최소 주문 금액이 **진짜로** 통하는지 돈 없이
  확인된다.
- 바이낸스: 리허설 호출이 따로 없으므로 계정 조회와 주문 규격 조회로 갈음한다.

리허설은 **모의와 실전 양쪽에서** 돈다. 실전에서 실패하면 주문을 하나도 내지 않고
멈춘다. 모의에서 실패하면 경고만 남기고 계속 돈다 — 모의는 키 없이도 돌 수 있어야
연습이 되기 때문이다.

### 5.4 화면

실행기의 실행 모드가 거래소에 따라 달라진다.

- 바이낸스: `모의` · `테스트넷` · `실전` 셋
- 업비트 · 빗썸: `모의` · `실전` 둘

기본값은 늘 모의다. 실전은 지금 메인넷과 같은 확인 절차를 거친다.

## 6. 키와 거래소 선택

### 6.1 지금 모양

`runner/credentials.py` 는 `FIELDS = ("api_key", "api_secret", "member_key")` 를
DPAPI 로 감싼 파일 하나에 평평하게 둔다.

### 6.2 v2

거래소별로 한 쌍씩 둔다.

```
{"version": 2,
 "member_key": "...",
 "exchanges": {"binance": {"api_key": "...", "api_secret": "..."},
               "upbit":   {"api_key": "...", "api_secret": "..."},
               "bithumb": {"api_key": "...", "api_secret": "..."}}}
```

`_ENTROPY` 는 `ggparrot-runner-credentials-v1` 그대로 둔다. DPAPI 엔트로피를 바꾸면
기존 파일이 **열리지 않아** 이사할 수 없다.

### 6.3 이사

v1 파일을 읽으면 `api_key`/`api_secret` 을 `exchanges.binance` 로 옮기고
`member_key` 는 그대로 둔다. 한 방향이고, 되돌리지 않는다. 옛 실행기로 돌아가는
사용자는 키를 다시 넣는다(회원 키는 살아 있다).

### 6.4 어느 키를 쓰나

매크로의 `exchange` 가 고른다. 사용자가 고르지 않는다 — 매크로가 이미 거래소를
가리키고 있으므로 묻는 것은 틀릴 기회를 주는 것뿐이다. 해당 거래소 키가 없으면
그 칸을 비워 보여 주고 시작을 막는다.

## 7. 서버

### 7.1 문을 연다

`_require_binance_macro` 를 **실행기 버전 조건으로 바꾼다.** 지우는 것이 아니다 —
구버전 실행기는 국내 주문을 낼 줄 모르므로 여전히 막아야 한다.

- 호출 세 곳(세션 시작 · 티켓 발급 · 티켓 청구)과 `claim` 의 방어적 검사 한 곳.
- 국내 매크로 + 실행기 버전 < 10 → 426 과 "실행기를 업데이트해 주세요".

`RUNNER_UNSUPPORTED_RULES`(C · K)는 그대로 둔다. 거래소와 무관한 제약이다.

### 7.2 신호의 시세

`runner_engine.py` 가 `get_ticker_price_cached(live.driver.symbol)` 을 **거래소 없이**
부른다. `data.get_ticker_price_cached` 는 이미 `exchange` 키워드를 받으므로 매크로의
거래소를 넘기면 끝난다.

### 7.3 버전

`runner/installation.py` 의 `RUNNER_VERSION` 을 `"9"` 에서 `"10"` 으로 올린다.
`SIGNAL_MIN_VERSION`(8)은 그대로 두고 `DOMESTIC_MIN_VERSION = "10"` 을 따로 둔다 —
지표형 신호와 국내 주문은 다른 능력이고, 한 숫자로 묶으면 나중에 못 가른다.
`supports_signals` 와 같은 꼴의 `supports_domestic` 을 둔다.

## 8. 실패 다루기

### 8.1 허용 IP

업비트 · 빗썸은 **호출지 IP 를 허용 목록에 등록해야** 한다(업비트는 키당 10 개).
데스크톱 실행기는 가정집 IP 라 바뀐다. 이건 우리가 없앨 수 없는 제약이고, 숨기면
사용자가 "키를 잘못 넣었나" 를 헤맨다.

- 인증 실패를 "API 키가 틀렸어요" 로 뭉뚱그리지 않고 **허용 IP 를 먼저 말한다.**
- 리허설이 이 실패를 **주문 전에** 잡는다(§5.3).

### 8.2 권한과 최소 주문 금액

`GET /v1/orders/chance` 가 `min_total` 과 수수료율을 준다. 주문 규격으로 쓰고,
매크로의 주문 금액이 `min_total` 에 못 미치면 시작할 때 막는다 — 주문을 보내고
거절당해 알게 되면 그 사이에 신호를 놓친다.

### 8.3 주문 상한은 통화마다 다르다

실행기에 1 회 주문 상한 `MAX_ORDER_USDT = 100` 이 있고 네 곳에서 쓰인다 — 주문 수량
계산, 매크로 자본의 기본값, `RiskGuard` 의 기준 자본, 시작 로그.

원화 시장에 이 숫자를 그대로 쓰면 **1 회 주문이 100 원**이 된다. 업비트의 최소 주문
금액(5,000 원)에 못 미쳐 **모든 주문이 거절된다.** 상한을 통화별로 가른다.

- `MAX_ORDER_USDT = 100` (그대로)
- `MAX_ORDER_KRW = 150_000` (100 USDT 와 비슷한 자리수)
- `order_cap(quote)` 하나가 고르고, 네 곳이 모두 이것을 쓴다

숫자를 통화와 떼어 두면 다음에 또 틀린다. 상한은 늘 통화와 함께 다닌다.

## 10. 테스트

### 10.1 바이낸스가 안 바뀌었다는 증명

`runner/test_macro_runner_execution.py` 의 시험 20 개가 **본문을 한 줄도 고치지 않고**
녹색이어야 한다. 이 시험들이 붙드는 것은 구현이 아니라 동작이다 — 미확정 제출을 두
번 보내지 않기, 부분 체결 보존, 기초자산 수수료 차감, 먼지 수량, 모호한 청산.

바뀌는 것은 `bot()` 도우미 **한 곳**뿐이다. 지금 이 도우미는 `bot.client = Mock()`
을 두고 각 시험이 `bot.client.futures_create_order` 를 직접 단언한다. 도우미가
날 Mock 을 `BinanceBroker` 로 감싸 `bot.broker` 에 꽂고 `bot.client` 는 그 날 Mock 을
가리키게 두면, 시험 본문 20 개가 글자 그대로 남는다.

이것이 이 작업의 유일한 안전 기준이다. 시험 **본문**을 고쳐야 할 일이 생기면 그것은
이동이 아니라 변경이고, 멈추고 왜 그런지 적어야 한다.

### 10.2 국내 어댑터

가짜 HTTP 응답으로 검사한다. 실제 거래소를 부르지 않는다.

- 시장가 매수가 `volume` 이 아니라 `price`(원화 총액)로 나간다.
- 시장가 매도가 `price` 가 아니라 `volume` 으로 나간다.
- 주문 응답이 없을 때 **재주문하지 않고** 같은 `identifier` 로 조회한다.
- `acquired_qty == executed_volume` — 기초자산 수수료를 빼지 않는다.
- `avg_price` 가 `trades[]` 의 `Σ funds / Σ volume` 이다.
- `Σ trades.volume ≠ executed_volume` 이면 `fees_known` 이 거짓이다.
- 업비트와 빗썸이 같은 경로에 다른 베이스 URL 로 간다.

### 10.3 모의 모드

- 모의에서 **주문 엔드포인트가 한 번도 불리지 않는다** (세 거래소 모두).
- 모의 체결가가 그 순간 현재가이고 수수료율이 반영된다.
- 리허설 실패가 실전에서는 주문 없이 멈추고, 모의에서는 경고만 남긴다.

### 10.4 키

- v1 파일이 v2 로 이사하고 회원 키가 살아남는다.
- 매크로의 거래소에 맞는 키가 선택된다.
- 키가 없는 거래소의 매크로는 시작이 막힌다.
- 어느 경로로도 거래소 비밀키가 서버 페이로드에 들어가지 않는다 — 기존
  `test_macro_runner_single_instance.py` 의 불변식을 거래소 셋으로 넓힌다.

### 10.5 서버

- 국내 매크로 + 실행기 v9 → 426.
- 국내 매크로 + 실행기 v10 → 통과.
- 신호 시세가 매크로의 거래소로 조회된다.
