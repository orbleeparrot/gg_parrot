# 묶음 실거래 — 레그마다 세션 하나, 서버가 나눈다

2026-10-30. 추천 묶음과 물어볼까의 묶음 카드는 지금 백테스트·모의까지만 된다. 서버가
묶음 매크로의 실행을 막고 있다(`PORTFOLIO_UNSUPPORTED_DETAIL`) — 실행기의 `Bot` 이
종목 하나 · 브로커 하나 · 엔진 하나이기 때문이다.

## 고른 길

실행기를 "한 세션에 봇 N개" 로 고치지 않는다. **묶음 하나를 레그마다 세션 하나로 쪼갠다.**

```
묶음 매크로(BTC 50% · ETH 50%)
   ↓ 실행기가 레그 수만큼 시작을 보낸다(원본 매크로 + leg_index)
서버 ── 서명을 **원본 전체**로 확인 → 레그 매크로를 만들어 세션에 저장
   ↓ 시작 응답의 leg_macro
실행기 ── 레그마다 평범한 단일 종목 봇 하나
```

### 왜 이 길인가

* **실행기의 매매 루프를 건드리지 않는다.** 실거래 코드에서 가장 위험한 자리다. 레그
  하나는 지금까지 돌려 온 것과 **똑같은 단일 종목 실행**이다. 종료 · 안전망 · 설정 변경 ·
  heartbeat 가 전부 그대로다.
* **서명이 깨지지 않는다.** 실행기가 매크로를 쪼개 보내면 그 레그 매크로는 원본과 달라
  `macro_digest` 가 어긋나고, 모든 묶음이 "고쳐서 돌린 파일" 로 기록된다. 그래서 실행기는
  **원본을 그대로** 보내고 쪼개기는 서버가 한다.
* **자금 분배를 서버가 셈한다.** 한 곳에서 셈해야 레그 금액의 합이 묶음 금액과 어긋나지
  않는다.

### 안 되는 것 — 묶음 한도

`bundle_risk`(동시 보유 종목 수 · 총 노출 한도)가 걸린 묶음은 **계속 거절한다.** 그건
레그끼리 "지금 몇 개 들고 있나" 를 물어야 하는데, 세션이 갈라져 있으면 물을 자리가 없다.
거짓으로 돌리느니 거절하고 이유를 보여 준다.

추천 묶음과 물어볼까의 묶음 카드는 한도를 걸지 않는다 — 그래서 이 길로 전부 돌아간다.

## 레그 매크로

원본에서 레그 하나만 남긴 **단일 종목 매크로**다.

| 칸 | 값 |
|---|---|
| `symbol` | 레그의 종목 |
| `legs` · `symbols` | 없음(단일 종목이 된다) |
| `params.initial_capital` | 묶음 금액 × 레그 비중 ÷ 100 |
| `rule_type` · `params` | 레그가 덮어썼으면 그 값, 아니면 묶음 값(`Macro.leg_rule`) |
| `entry_filter` | `Macro.leg_filter` 가 정한 값 |
| 나머지 | 원본 그대로(거래소 · 시장 · 방향 · 레버리지 · 봉 간격 · 기간 · 수수료) |

## 묶었다는 사실을 남긴다

세션마다 `bundle_key`(묶음 하나의 식별자) · `bundle_index` · `bundle_size` · `bundle_digest`
(원본 매크로의 지문)를 적는다.

* [내 에이전트]가 레그 N개를 **한 줄로 묶어** 보여 준다.
* **묶음 종료** 가 레그 전부에 종료를 건다 — 반만 남는 것이 가장 나쁘다.
* 증빙에도 원본 지문이 남아, 나중에 "무엇을 돌렸나" 를 원본으로 되짚을 수 있다.

`bundle_key` 는 실행기가 만든다(한 번의 시작 묶음에 같은 값). 서버가 만들면 레그마다
다른 값이 나온다 — 시작 요청이 레그마다 하나씩 오기 때문이다.

## 실패를 어떻게 다루나

레그 셋 중 하나가 시작에 실패하면 **나머지는 그대로 둔다.** 되돌리려고 이미 들어간
주문을 급히 정리하는 쪽이 더 위험하다. 대신 화면이 "3개 중 2개만 시작했어요" 를 말하고,
사용자가 보고 정하게 한다.

## 안 하는 것

* 레그끼리 자금을 옮기는 것(한쪽이 손실이라 다른 쪽을 키우는 식).
* 묶음 전체의 손익을 하나의 숫자로 다시 셈하는 것 — 레그별 숫자를 더해 보여 준다.
