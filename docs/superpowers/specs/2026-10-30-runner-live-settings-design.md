# 구동 중 매크로 설정 변경 — 실행기 화면 · 에이전트 화면(원격)

2026-10-30. 사장님 요청: 실행기에서 구동 중인 매크로의 금액·조건을 바꿀 수 있게, 그리고
에이전트 화면에서도 원격으로 같은 변경이 되게. **수정 사실은 우리 쪽에 증빙으로 남겨야
한다** — 사용자가 고쳐서 잘못 돌았을 때 책임 소재를 가리는 근거다.

## 지금 구조에서 확인한 것

* **판단은 서버가 한다.** `runner-core/src/bot.rs`: "진입/청산 판단은 서버가 함. 로컬에
  남은 판단은 안전망(손절 %, 일일 손실, 최대 보유시간)뿐임." 실행기가 직접 판단하는
  모드(`decides_locally`)는 환경변수로 꺼져 있다. 따라서 **조건의 주인은 서버**다.
* **원격 명령 통로가 이미 있다.** 웹이 `request_stop` 으로 `stop_mode` 플래그를 세우고,
  실행기가 다음 heartbeat 응답의 `action` 으로 받아간다(최대 `POLL_SECONDS`=5초 지연).
* **전략을 다시 세우는 길이 이미 있다.** `runner_engine._start_driver` 는 DB 의
  `macro_json` 으로 드라이버를 만들고 → 과거 봉으로 웜업 → `driver.restore(state)` 로
  포지션·장부를 복구한다. 재기동·배포 때 쓰는 길이다.
* **지표는 웜업이 다시 만든다.** `strategy_state` 에는 웜업이 못 만드는 것만 담긴다
  (candles.py 주석). 그래서 **지표 기간을 바꿔도 새 값으로 다시 쌓인다** — 이 설계가
  성립하는 이유다.
* **수정 여부를 가리는 장치도 이미 있다.** `macro_signing` 이 같은 문제(내려받은 파일을
  고쳐 돌리고 문의하는 경우)를 풀려고 만들어졌고, 세션에 `macro_origin` · `macro_digest`
  를 남긴다.

## 하는 일

변경은 **언제나 서버를 거친다.** 실행기 화면에서 바꿔도 실행기가 서버에 요청하고, 서버가
확정한 뒤 돌려준다. 실행기가 혼자 바꾸면 서버 전략과 실행기 설정이 갈라진다 — 그 둘이
갈라지면 어느 쪽이 진짜인지 아무도 모른다.

```
웹(에이전트 화면) ─┐
                   ├─→ POST /api/me/runner/sessions/{id}/settings
실행기 화면 ───────┘        │
                            ├─ 바꿀 수 있는 값인가 검사
                            ├─ 새 macro_json 저장 + 새 서명/지문
                            ├─ 변경 기록 한 줄 적립(증빙)
                            └─ 전략 드라이버 재시작(웜업 → 포지션 복구)
                                     │
실행기 ←── heartbeat 응답의 settings ─┘   (금액 · 안전망 갱신, 최대 5초)
```

## 바꿀 수 있는 것 / 없는 것

| | 바꿀 수 있나 | 왜 |
|---|---|---|
| 투자 금액(`initial_capital`) | 된다 — **다음 진입부터** | 이미 들어간 포지션 크기는 못 바꾼다. 그건 추가 매수·부분 청산이고 다른 일이다. |
| 방식별 조건 값(익절 %, RSI 기간·문턱, 이동평균 기간, 밴드 폭 …) | 된다 | 전략 재구성 + 웜업으로 반영된다. |
| 위험 설정(손절 %, 일일 손실, 최대 보유시간, 투자 비율) | 된다 | 서버 전략과 실행기 안전망 양쪽에 반영한다. |
| 매매 방식(`rule_type`) | **안 된다** | 다른 매크로다. 종료하고 새로 시작하는 게 맞다. |
| 종목 · 거래소 · 시장 · 방향(롱/숏) · 레버리지 | **안 된다** | 포지션의 정체가 바뀐다. 들고 있는 포지션과 어긋난다. |
| 봉 간격(`candle_interval`) | **안 된다** | 판정의 시간 축이 바뀐다 — 사실상 다른 매크로다. |

### 포지션을 들고 있을 때

금액 변경은 늘 "다음 진입부터" 다. 조건 변경은 사용자가 고른다.

* **지금 적용** — 들고 있는 포지션의 청산 조건도 새 값으로 바뀐다. 화면이 그렇게 말한다.
* **이 포지션 정리된 뒤부터** — 예약해 두고, 포지션이 비는 첫 heartbeat 에서 적용한다.

포지션이 없으면 묻지 않고 즉시 적용한다.

## 증빙 — `RunnerSettingChange`

**세션이 지워져도 남는다.** 이것이 이 테이블의 존재 이유다. `_delete_session_rows` 는
`RunSessionEvent` · `RunnerCommand` 를 세션과 함께 지우고, 보존 작업
(`prune_ended_sessions_batch`)이 끝난 세션을 주기적으로 지운다. **변경 기록은 거기 끼지
않는다** — 시험이 이 성질을 고정한다. 세션 번호는 외래키가 아니라 그냥 숫자로 남긴다.

한 줄에 담는 것:

| 칸 | 뜻 |
|---|---|
| `user_id` · `created_at` · `created_ms` | 누가 · 언제 |
| `source` | `web`(에이전트 화면) \| `runner`(실행기 화면) |
| `session_id` · `user_macro_id` · `symbol` · `exchange` | 어느 실행의 무엇을 |
| `before_json` · `after_json` | 바꾸기 전 · 후의 **매크로 전체** |
| `before_digest` · `after_digest` | `macro_signing.digest` 지문 — 기존 출처 판별과 같은 자 |
| `changed_fields` | 바뀐 칸 이름들(사람이 읽는 요약) |
| `apply_mode` | `immediate` \| `next_entry` |
| `in_position` · `position_qty` · `entry_price` · `unrealized_pct` | **그때 포지션을 들고 있었는지** |
| `runner_version` | 어느 실행기였는지 |
| `applied_ms` | 실행기가 반영을 확인한 시각(0 이면 미확인) |

세션에도 흔적을 남긴다 — `macro_origin` 은 시작 시점의 출처라 "시작 뒤에 고쳤다" 를
표현하지 못한다. `settings_changed_count` 를 올리고 `macro_digest` 를 새 지문으로 바꾼다.
에이전트 화면과 실행기 화면 모두 "이 실행은 구동 중 N번 수정됐어요" 를 보여 준다.

**추가만 하고 고치지 않는다.** 갱신하는 칸은 `applied_ms` 하나뿐이다.

## 실행기가 받는 것

heartbeat 응답에 `settings` 를 싣는다 — 실행기가 쓰는 값만: 투자 금액, 안전망(손절 %,
일일 손실 %, 최대 보유시간), 투자 비율, 그리고 적용 기준 시각. 실행기는 받은 값으로
안전망과 주문 크기를 갱신하고 다음 heartbeat 에 확인을 올린다(서버가 `applied_ms`).

**버전 관문**을 둔다. 이 기능을 모르는 옛 실행기는 `settings` 를 무시하므로, 서버 전략만
바뀌고 실행기 안전망은 옛 값으로 남는 **어긋남**이 생긴다. 그래서 최소 버전에 못 미치는
실행기가 붙은 세션은 변경 요청 자체를 거절한다("실행기를 업데이트해 주세요").

## 범위 밖

* `decides_locally` 모드는 지금 꺼져 있다. 그 모드에서는 매크로 전체를 실행기로 내려
  보내야 하므로 따로 잡는다.
* 포지션 크기 자체를 바꾸는 것(추가 매수 · 부분 청산)은 이 작업이 아니다.
* 매크로 라이브러리(`UserMacro`)의 원본은 건드리지 않는다. 바뀌는 것은 **이 실행**뿐이다.
  라이브러리까지 바꾸면 다음 실행이 조용히 달라진다.
